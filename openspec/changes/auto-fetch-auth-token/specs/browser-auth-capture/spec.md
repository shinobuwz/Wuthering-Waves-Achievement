## 新增需求

### 需求:自动获取按钮
设置页通用认证设置区域必须提供「自动获取」按钮。点击后必须弹出内嵌浏览器对话框，打开 `https://www.kurobbs.com/`，供用户登录。

#### 场景:点击自动获取
- **当** 用户点击「自动获取」按钮
- **那么** 弹出内嵌浏览器对话框，加载 `https://www.kurobbs.com/`

#### 场景:已有登录态时直接触发拦截
- **当** 弹窗打开时浏览器 profile 已保存登录态
- **那么** 页面加载时自动发起 API 请求，拦截器触发，凭据自动填入，弹窗关闭

### 需求:请求头凭据拦截
内嵌浏览器必须拦截所有 HTTP 请求头，当检测到同一请求同时包含非空的 `devcode` 和 `token` 字段时，必须自动提取这两个值。

#### 场景:成功拦截凭据
- **当** 浏览器发出的请求头中同时包含非空的 `devcode` 和 `token`
- **那么** 系统提取这两个值，填入设置页对应输入框，关闭浏览器弹窗，并显示成功提示

#### 场景:未登录时无凭据请求
- **当** 用户尚未登录，页面发出的请求头中不含 `devcode` 或 `token`
- **那么** 拦截器不触发，弹窗保持打开，用户继续完成登录流程

### 需求:登录态持久化
内嵌浏览器必须使用独立的命名 profile（`kurobbs_auth`），使得用户的登录 cookie 在多次点击「自动获取」之间得以保留，无需每次重新扫码登录。

#### 场景:再次打开弹窗时已登录
- **当** 用户曾经完成过一次登录，再次点击「自动获取」
- **那么** 浏览器 profile 中保有登录态，页面加载后自动发起认证请求，凭据被自动拦截填入

#### 场景:首次使用时无登录态
- **当** 用户首次点击「自动获取」，profile 中无登录态
- **那么** 弹窗打开 `https://www.kurobbs.com/`，用户手动完成登录后触发凭据拦截
